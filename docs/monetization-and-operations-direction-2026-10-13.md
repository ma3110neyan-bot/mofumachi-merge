# 収益化・運営の将来設計

2026-10-13（日本時間）のユーザー指示を反映。**今回は設計のみ。広告・課金・ガチャUI・分析SDK・テナント収入・有料／無料Gemsの保存を実装していない。** 現在の街→Merge→フォント→2.5D設計を継続し、基本ループとPixel安定を最優先にする。

## 導入順と無料プレイ

| 順 | 将来の機能 | 導入するための確認 |
|---|---|---|
| 1 | 任意視聴型広告 | 基本操作・保存が安定。追加報酬の価値と任意選択の分かりやすさを確認 |
| 2 | 少額Gems販売 | ゲーム内の使い道、購入・復元・重複防止を検証 |
| 3 | 初心者パック | 少量Gems・便利品・装飾を明示し、無料進行を維持 |
| 4 | 限定装飾・衣装 | かわいさと収集を楽しむ。正式キャラを壊さない素材確認 |
| 5 | イベント・ガチャ | D1／D7継続と遊びの定着を確認して採否判断 |

強制広告と進行必須の課金は採用しない。現在の無料生成を維持する。まだ存在しないスタミナ・待ち時間を広告のために先行追加しない。Coinsは日常の買い物・街運営、Gemsは少し便利・特別な品、有料課金はGems補充と限定装飾・衣装という役割。

## 後から接続する境界

現在の実コードにはItemCatalog、QuestDefinition、QuestManager、RewardService、GameState／SaveService、IStateStore、UIFlowControllerがあり、既存の保存失敗時の復元と報酬IDの重複防止を使う。将来の機能は専用カタログ・取引サービス・プラットフォームアダプターとして接続し、UIで金額だけを減らす処理を追加しない。

| 将来の境界 | 責務とデータの候補 |
|---|---|
| ItemData／装飾・衣装カタログ | 安定itemId、category、rarity、eventId。MergeのLv.や同種同Lv.ルールとレアリティを別にする |
| Reward取引 | transactionId、source、grant内容、受取済みID。納品報酬と広告追加報酬を別IDにして基本報酬を再払いしない |
| Shopサービス | 商品ID・カタログ版・価格・在庫・所持条件を変更前に検査。支払いと全品付与を1保存、失敗は全復元 |
| Wallet | Coins、freeGems、paidGems、消費順、残高・取引履歴を同じ取引で扱う。Gems消費順は将来の設計確認で決定 |
| 広告／購入アダプター | 完了した広告・検証済み購入だけを一度付与。中断・失敗・再試行・二重通知で二重払いしない |
| 分析アダプター | コアが保存に成功した操作の後へ接続。送信失敗で合成・納品を戻したり止めたりしない |

今回は上のインターフェースや空のSDKラッパーを製品コードに増やさない。後続実装時に、既存の成功結果とIStateStoreの境界へ必要なものだけを追加する。

## 将来のガチャ／イベント

レアリティはNormal／Rare／SuperRare／UltraRare（表示：ノーマル／レア／スーパーレア／ウルトラレア）。対象は装飾・衣装・Merge補助・イベント限定品。正式6名そのものを別の顔や配色へ置き換える抽選にしない。

イベント定義はeventId、catalogVersion、startDate／endDate（保存はUTC、画面は日本時間等の利用者時間帯）、対象一覧、有限の非負weight／probability、duplicatePolicyを持つ設計とする。全weightが0、終了が開始以前、存在しない品物、期間外の抽選は成立させない。確率値は未決定で、バランス確認後に提示する。

重複は保有・交換・変換のどれかを品物ごとに明示。履歴は抽選ID・時刻・イベント／カタログ版・消費した有料／無料Gems・付与品・重複処理を記録する。支払い・付与・重複処理・履歴を一括取引にし、途中失敗や同じ要求IDの再送で残高と品物を二重変更しない。乱数結果を再試行のたびに引き直す方式は使わない。

## SaveDataの移行

現在の保存はv3、Gemsは単一残高。今回はその形式と既存セーブを維持する。将来の通貨区分・施設・履歴は新しい保存版と明示的な移行処理を設計・承認してから追加する。旧残高から有料／無料の内訳を推測せず、購入記録がない残高の移行区分を先に決める。

移行・購入・広告付与・抽選・テナント受取は、支払い／残高／所持品／履歴／受取時刻を1回の保存で確定する。旧セーブの読込み、移行失敗、通信中断、保存失敗、再起動、同一取引IDを検証する。読めない新しい形式を古い版で上書きして履歴を消さない。新機能が未実装なのに保存項目を先行変更したとは報告しない。

## テナント収入：ゲーム内Coinsの候補

ショップ建設→時間経過→収入受取→Coins→改装→街の景色、という日常の楽しさを候補にする。実際の売上・課金収益とは別のゲーム内経済で、現在のショップ入口は販売準備中のまま。

将来の定義はfacilityId、店舗Lv.、周期・収入額・上限、解放条件、改装段階、キャラ利用と会話、eventId。保存には建設・改装状態、受取基準UTC、未受取と取引IDを設計する。時計が戻った場合は負の収入を作らず、長いオフライン期間の上限をバランス確認で決める。受取のCoinsと基準時刻を一括保存し、保存失敗時は両方戻す。受取を連打・再起動しても同じ期間の収入を重ねない。

今回のTownPlaceCatalogは保存済み街Lv.から場所を再構築する読み取り専用データ。将来はそこへ施設の訪問場所を足せるが、現在の散歩場所を「建設済み有料施設」と読み替えない。

## 公開後の測定と判断

| 指標 | 定義・見ること |
|---|---|
| DL／新規開始 | ストアDLとゲーム初回開始を分ける |
| D1／D7継続 | 初回開始日を基準に同じ定義・期間の利用者群で比較 |
| プレイ時間 | foregroundの実プレイ、pause／backgroundを除外 |
| 街の成長 | 到達Lv.、章・依頼の離脱箇所、拡張場所の利用 |
| Merge | 保存成功の合成回数、生成種類、満杯・拒否理由、納品までの時間 |
| ショップ | 閲覧→確認→保存成功の購入。失敗と取消を購入へ数えない |
| 広告 | 提示→任意選択→視聴完了→付与成功を分ける |
| 課金 | 検証済み購入・付与・復元を識別し、同じ購入を二重集計しない |

イベント例はsession_started／session_ended、merge_committed、quest_delivered、town_level_reached、shop_opened／purchase_committed、ad_opted_in／ad_reward_committed。安定eventIdとschemaVersionで再送を識別し、低負荷のバッファと送信停止が可能なアダプターへ接続する。現行QA入力ログは操作の調査用で、継続率分析や課金履歴の代用ではない。

DLだけで機能を追加せず、D1／D7、プレイ時間、進行到達、フリーズ・クラッシュ、広告／購入の利用率を同じ利用者群で評価する。数値基準は公開後の基礎データを見て決め、定着不足なら街・Merge・依頼の遊びを先に改善する。SDK導入時には実際の送信項目・保存期間・Google Play申告を確認する。
