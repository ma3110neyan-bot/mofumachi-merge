## 2. 生成処理と消費の最小接続点

### 現行経路

生成ボタン（QuestMergeScreens.cs:135–142） → GenerateFromFrame（UIFlowController.cs:504–505） → GenerateItem（同:463–470） → GameStateManager.AddItem（:21） → MergeBoard.AddItem（:22–27）。CreateTeaもGenerateItemへ集約される。

- UI側は操作可否・正式ItemCatalog・生成枠配置を確認。追加後のboolで成功表示・SEを分ける。
- MergeBoardは空きかつロックされていない最初のマスへ追加。空きがなければfalseで、盤面は変化しない。
- GameStateManager.Mutate（:78–90）はロック→状態と盤面ロックの退避→操作→依頼進捗更新→保存。保存成功でtrue。IO/権限エラーではCopyFromとロック復元でfalse。
- UIは失敗時、LastErrorがあれば保存エラー、なければ盤面満杯の案内を表示する。
- 注意：Mutateは操作自体がfalseなら即returnし、その場合のrollbackは行わない。新処理で「先に減算→追加失敗→false」は禁止。

### 消費の提案

GameStateManagerに生成専用の入口を置き、入力検証・残高確認→Board.AddItem成功→仮減算→盤面と残高を同時保存→成功返却とする。保存成功をもって生成と消費の両方を確定し、失敗なら両方戻す。

**Game.AddItem成功後にUIで別途減算・別保存しない。** 成功追加の前にPを引かない。汎用AddItemは初期配置・テスト準備等でも使われるため、一律課金せず、生成専用入口だけ課金する。合成・移動・納品はこの入口を通さない。

## 4. 街Lv判定の最小構造

現行の結合はTownGrowthService.cs:6の「現在LvとcompletedQuestIds.Countの大きい方」。QuestManager.TryDeliverの:98から呼び出される。12件化だけ先に有効にすると、数値の街Lvが12まで増え得る。見た目の成長段階は6までなので両者が不整合になる。

提案：TownGrowthServiceにLv1〜6の閾値表を集約し、登録された進行対象の完了ID数と独立した街行動累計値を使う。「必要依頼数AND必要累計値」を満たす最大段階を求め、**保存済み街Lvとその結果の大きい方**を採用する。所持Pは参照しない。既存Lvを下げたり、累計不足を理由に街グラフィックを戻したりしない。移行で架空のポイントや完了IDを足して帳尻を合わせない。

街行動累計が後から条件を満たす場合もあるため、納品保存時だけでなく、対象行動のポイント・累計・取得済み記録を保存する同一処理でも成長評価する。納品済みだが累計不足なら、その不足を案内する。成長なしの納品でQuestState.TownGrownや「街が成長しました」を無条件に使わない。

既存QuestStateの列挙値は保存対象なので削除・並べ替えをしない。成長した場合／しなかった場合の保存状態と表示分岐を最小変更で定義する。日次回復・購入・初期配布は累計に加えない先行案だが、正式名称と対象行動の確定はまだ必要。

### 2ファイルを一括保存しない最小連携案

経済の残高・累計・取得済みは主セーブを正本とし、社会記録は交流・お花の既存正本のまま維持する。UIFlowControllerで既存社会保存の成功を受け取り、経済側の独立した重複判定を通して主セーブへ保存する。2ファイルが同時確定するとは扱わない。

- 会話：主保存失敗時はP成功通知を出さず、同じキャラへの次の会話で未取得だけを再評価する案。既存交流記録を巻き戻さない。
- お花：保存済み受領日と主側の消込日を照合する案。導入以前の全履歴を一括換金しない。導入当日すでに受領済みの場合の扱いは未確定。
- 散策：日付付き完了IDの二重通知を拒否し、通常・追加回数と同時保存する。既存の引数なしRecordWorldWalkだけでは識別情報が不足するため、接続箇所の限定拡張が必要。
- 既存journalの形式・Validate・保存器を通貨用に改造しない構成を推奨。完全に一つの保存へ統合する大改修は提案しない。

### 端末日付変更への現状

- **存在する**：Day以下の日付ではリセットしないため、同日再読込・時計後退だけで今日のお花を再受取することはできない（TownDailyProgress.cs:44–49）。
- **未実装**：端末日付を未来へ進めて別日を繰り返す行為の防止、信頼できるサーバ時刻、前進量の検証。読んだ経路はDateTime.Nowを使用する。
- 未来日保存後に時計を戻すと、保存Dayに追いつくまで日次更新が進まない可能性がある。これはコード上の挙動で、今回新しく再現・テストした不具合ではない。
- 最小候補は既存の非後退判定と主側の同日重複防止を維持し、疑わしい変更時のボーナス保留方針を決めること。ただしクライアント時刻のみで前進不正を完全防止したとは言えない。オフラインで許容する残余リスク・正当な日付変更時の復帰方法は未確定。
